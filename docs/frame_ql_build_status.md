## Language surfaces this build does not realize

Two rules are lawful Frame-QL that this build cannot run. Both are language-level rules; neither is
a defect in the Manual.

- **Filtering through a relationship-derived dimension** (language reference §4.1.1). The filter is
  pushed to the measure's own source table, which carries the universe's base coordinates and not the
  joined ones, so there is nothing there to bind against. Refused before execution with
  `filter_unsupported`, naming the base dimensions as the remedy. This is a fact about the build:
  rewording does not help, and the analytical reachability of the dimension is not in question.
- **The roadmap expression forms** (language reference §2.8). These are not part of the shipped envelope (columna-core 0.18.1).

**Query-error reason fidelity.** The query-error channel (language reference §7.3) carries two
jurisdictions — a request the language does not accept, and a valid, admissible request this
realization cannot carry out. **This build's `reason` does not reliably separate them.**
`cross_universe` and `type_error` carry their own reason and `unsupported` marks a realization
failure; every other language-invalid case reports `reason = "unknown"` and puts the information in
`detail`. The detail is precise; the reason is not yet a field to branch on. A second route exists
too: an unregistered operator (`wibble(revenue)`) reaches the caller as a raised error rather than as
a frame, so a caller that reads only frames will not see the whole channel. Both are interface facts
about columna-core 0.18.1, not language law — the language states the distinction, and this build's
wire does not yet express it fully.

**String literals.** Frame-QL treats `'east'` and `"east"` as one literal. This build normalizes the
predicate into the backend's spelling before it becomes SQL, so both forms run and return the same
rows; the substrate does not reinterpret Frame-QL's literals.

## How the examples are checked

Every Frame-QL example in the language reference is checked against the shipped parser (`columna_core.envelope.parse_statement`, columna-core 0.18.1) by `docs/tools/check_manual_frameql.py`, which rides the manuals merge as a standing test — the
reference can never document syntax its own parser rejects. A block fenced `frameql-illformed` is
deliberately ill-formed and the check asserts it does **not** parse.

## What ships

What ships through columna-core 0.18.1 is the envelope of Chapter 1 of the language manual with the
series forms of §§2.1–2.7: reductions with explicit input pins — single-level or a product grain —
maps, composite reductions, the anchor product, one universe per expression, every grain either
determined or pinned, and every answer one of the four dispositions (serve · disclose · clarify ·
refuse).

Every Frame-QL example in the language manual is checked by `docs/tools/check_manual_frameql.py`,
which plans each one through the real planning surface and executes the ones that plan to serve or
disclose (run against the shipped columna-core — 0.18.1 at this revision). An example presented as
executable is not validated until the stage at which its claimed behaviour is observable, so an
example documented to clarify or refuse must reach that outcome with the reason the prose names.

Read it alongside the two documents it answers to:

- [`frame_ql_language.md`](frame_ql_language.md) — what Frame-QL means, and what the language has
  ruled in. Independent of any build.
- [`core_profile.md`](core_profile.md) — what a conforming Core implementation undertakes. A promise,
  authored.

**Conformance** compares the two rightmost columns below. *conforms* — the build does what the Core
contract undertakes. *lag* — the build does less; a gap to close in the build. *exceed* — the build
does more; the contract is behind the implementation and should be updated. Neither lag nor exceed
changes the contract.

down natively or computed above the boundary by the framework — is recorded in the Columna Reference
Manual's connector matrix, which is that manual's own subject. Additional backends publish their own
column there when a connector ships, and not before.
