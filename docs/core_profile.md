# The Core Profile

**What a conforming Core implementation of Frame-QL undertakes to realize.**

This document is a contract, not a description. It says what an implementation must be able to do to
call itself Core; it does not say what any particular build currently does. Those are different
questions and mixing them is how documentation goes stale without anyone noticing — a build changes,
a sentence describing it does not, and nothing fails.

So the three questions are kept in three places:

| Question | Document | Written how |
|---|---|---|
| What does Frame-QL *mean*? | [`frame_ql_language.md`](frame_ql_language.md) | authored |
| What must a Core implementation *support*? | this document | authored |
| What does the shipped build *actually run*? | [`frame_ql_build_status.md`](frame_ql_build_status.md) | measured |

## Two rules govern this document

**A profile may add what an implementation can run. It may not change what Frame-QL means.** Every
capability named below exists in the canonical authority, and naming one that does not is an error
rather than an extension. A profile cannot invent a capability, redefine one, or make a proposed
construct part of the language by undertaking to run it.

**A build may meet this contract, fall short of it, or go beyond it — and does not rewrite it.** All
three happen and all three are visible in the build status document. A build that falls short has a
gap to close, not a contract to lower. A build that goes further has a contract to update, not a
licence to leave it stale.

## Capabilities this contract does not cover

Anything absent from the table is not undertaken by Core. That includes constructs the language has
ratified, which is a real gap rather than an oversight, and constructs the language has only
proposed, which nothing is obliged to run.

## Backends

Core defines what must be realizable, not how. Which backend runs a capability, and whether it does so
natively or through the framework, is recorded per connector in the build status document.
